# Closed test checklist (new personal accounts: 12+ testers opted in for 14 continuous days)
1. Wait for identity + phone verification in Play Console.
2. Create app: name "Patrol Radar", App, Free, accept declarations. Package `io.github.missionaryj.patrolradar`.
3. Setup → App signing: keep **Play App Signing** (default). The upload key is our keystore; the first AAB upload registers it.
4. `PLAY_SERVICE_ACCOUNT_JSON` is set to `play-release@patrol-radar-billing.iam.gserviceaccount.com` ([github-play-upload.md](github-play-upload.md)). That account can view this app and **Release apps to testing tracks**. It cannot release to production. A successful **Android APK** run on `main` uploads the signed AAB to **Internal testing** (`internal`) only. Closed testing (`alpha`) and Open testing (`beta`) happen when you run the workflow and choose that track. The workflow rejects production. If the secret is removed, the upload step skips with a notice.
5. Manual fallback while the secret is unset: GitHub → Actions → "Android APK" latest successful `main` run → artifact `patrol-radar-release-aab` (unzip → `patrol-radar-release.aab`). Upload that AAB by hand to Internal, Alpha, or Open testing. Never upload the debug APK. Never create a production release.
6. Testing → Closed testing → Alpha → Testers: an email list with **at least 12–15 Google accounts** (add a few spares; testers who drop out don't count). Do not create a second closed track for CI. The API id of this track is `alpha`. Internal testing has its own tester list for the builds that land on every `main` merge.
7. Release notes on every track are "We squashed bugs and improved performance so Patrol Radar is better for you". Internal publishes to internal testers without Send for review. Alpha and beta are held: open **Publishing overview**, click **Send for review**, then after approval click **Publish changes**. See [github-play-upload.md](github-play-upload.md).
8. Fill App content (Policy → App content): privacy policy URL, ads (no), app access (no login), content rating (content-rating.md), target audience 18+, data safety (data-safety.md), foreground service declaration (permissions.md, include a short screen video link, e.g. unlisted YouTube).
9. Store listing: paste listing.md text, upload icon-512.png, feature-graphic-1024x500.png, and the current UI screenshots `screenshots/01-map-dispatch.png` and `screenshots/02-map-mock.png` (2–8). Do not upload a Classic UI screenshot.
10. Send testers the opt-in link (Closed testing → Testers → "Copy link"). Each must open it, tap **Become a tester**, then install from Play.
11. Keep ≥12 testers opted in for 14 days straight; ask them to open the app a few times (Google looks at engagement).
12. After day 14: Dashboard → **Apply for production** and answer the questionnaire about the test (how testers were recruited, feedback, changes made). That application is a Play Console form. This GitHub workflow still cannot upload a production release.
13. Every new upload needs a higher versionCode. CI uses the Android workflow run number. Internal testing and Open testing are at version code 237; run numbers above 239 are ahead of that. `versionName` is `package.json` `version` and should be bumped for each release you want testers to distinguish. A re-run reuses the run number. A manual upload with a higher code blocks CI until the run number passes it. See [github-play-upload.md](github-play-upload.md).
